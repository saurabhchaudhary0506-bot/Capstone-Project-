Delhivery Last-Mile Delay Intelligence Pipeline

A connected pipeline on synthetic Delhivery parcel data. It estimates delivery hours (Part B), flags parcels likely to miss their promise (Part C), segments the 24 hubs (Part D), and turns a batch of new parcels into an action list. The data is synthetic; no real Delhivery records are used. Money is in Indian Rupees (INR).

How to run

Run every command from the repository root, in this order. Tested with Python 3.14.4, pandas 3.1.0, numpy 2.5.4, scikit-learn 1.9.1 and joblib 1.6.0 (pinned in requirements.txt).

python -m venv .venv

pip install -r requirements.txt

Data findings

All numbers below are copied from outputs/part_a_checks.csv, outputs/part_a_delay_by_group.csv and outputs/part_a_correlations.csv.

Service type: Express parcels are delayed most often, at a rate of 0.4897 (119 of 243). Standard is 0.2056 (132 of 642) and Economy is 0.0857 (27 of 315).
Hub tier: the delay rate rises steeply with tier: Tier 1 is 0.0400 (16 of 400), Tier 2 is 0.2150 (86 of 400) and Tier 3 is 0.4400 (176 of 400).
Distance: the delay rate climbs with lane distance: 0.0219 for 0-200 km, 0.1368 for 201-400 km, 0.4364 for 401-600 km and 0.8523 for 601+ km.
Strongest correlations with delivery_hours: promised_hours (0.8372), distance_km (0.4013) and n_stops (0.3247). Longer promises, longer lanes and more rider stops mean more hours. hub_daily_capacity (-0.3237) is a very close fourth.
Log transform: declared_value_inr was log-transformed because it is right-skewed: its mean is INR 1,533.05 (1533.0542 in the file) against a median of INR 1,121.50, while after the log the mean (7.0277) and median (7.0224) are nearly equal.

Cleaning summary (from part_a_checks.csv): 1,224 raw rows, 24 exact duplicates removed, 1,200 rows kept, 5 scanner-fault weight sentinels treated as missing, 12 service-type spellings reduced to 3, and 0 missing values across the 17 features and the targets. The overall delay rate is 0.2317 (278 delayed parcels).

Model results
Regression

Source files: outputs/part_b_metrics.csv, part_b_tree_depth.csv, part_b_gb_learning_rate.csv, part_b_cv.csv, part_b_checks.csv.

Split and leakage check: 840 / 180 / 180 rows. The scaler was fitted on training rows only: the largest absolute column mean is about 0 on the scaled training rows and 0.2187 on the scaled test rows.
Baseline: predicting the training mean for every parcel gives a validation R² of -0.0212. That is slightly below zero: it explains none of the variation in delivery hours, so any real model has to beat it.
Validation winner: linear regression had the lowest validation RMSE, 4.8912 hours (R² 0.9313). Gradient boosting was almost tied at 4.9165 hours (R² 0.9306). Random forest scored 5.4680 hours (R² 0.9141) and the decision tree 6.2796 hours (R² 0.8867).
Bias and variance (tree depth): the gap is validation RMSE minus training RMSE.

2	9.3687	10.4114	1.0427
3	7.5295	8.7033	1.1738

Depths 1 and 2 are high-bias: both errors are high and close together, so the tree is too simple to learn the pattern. Depths 12 and unlimited are high-variance: training error falls towards 0 while validation error rises, a gap of 6.0560 and 7.7890, so the tree memorises the training rows. Depth 8 is a transition case (gap 3.5025, validation RMSE already rising). Depth 6 is the sweet spot with the lowest validation RMSE (6.2796), and it is the depth used for the decision tree in the model comparison.
Learning rate (gradient boosting, 100 trees): 0.1 was best (validation R² 0.9306, RMSE 4.9165). At 0.01 the model learns too slowly: 100 small steps are not enough to get close, and R² is only 0.7127 (RMSE 10.0018). At 1.0 each tree takes a full-size step and overshoots, so the ensemble becomes unstable and R² drops to 0.8440 (RMSE 7.3701).
Cross-validation (5-fold, one shared KFold object, 1,020 training-plus-validation rows): linear regression has a mean R² of 0.9261 (std 0.0048) and gradient boosting 0.9352 (std 0.0044). The cross-validation ranking therefore disagrees with the validation ranking.
Which model I would ship: gradient boosting. The validation ranking rests on one 180-row split, where the two models differ by only 0.0007 in R². The cross-validation average uses all 1,020 rows across five different splits, so it is the more reliable comparison, and it favours gradient boosting by 0.0091 R² with a similar spread. The delivery-hours process also contains interactions (for example the sale-window effect on Express parcels, and long-distance lanes in rain) that a linear model cannot represent but a boosted tree can. The margin is small, so this is not a strong preference; linear regression is a sound fallback because it is simpler to maintain.
Final test score, stated honestly: following the validation rule, the validation winner (linear regression) was scored once on the 180 test rows: R² 0.9493, RMSE 4.5235 hours, MAE 3.5671 hours. That test score belongs to linear regression, not to the gradient boosting model I would ship. I did not score gradient boosting on the test rows, because choosing a model after looking at test results would make the test set no longer independent. The test score is a guide to the accuracy level of this model family, not a measured result for gradient boosting.

Classification

Source files: outputs/part_c_models.csv, outputs/part_c_feature_scores.csv, outputs/part_c_selectk.csv, outputs/part_c_tuning.csv, outputs/part_c_thresholds.csv, outputs/part_c_final_test.csv, outputs/part_c_final_config.csv.

Split and leakage check: 840 / 180 / 180 rows (train / val / test), 195 / 42 / 41 delayed parcels. The selector (SelectKBest, k = 7) was fitted on training rows only; test rows were never used until the single evaluation in Task 7.

Blind baseline: predicting "on time" for every parcel gives 76.67 % accuracy (TN 138, FP 0, FN 42, TP 0) but catches zero delayed parcels. Accuracy alone hides a useless model — this is why we optimise for recall and F1, not accuracy.

Feature signal: SelectKBest (F-test) and RandomForest importance agree on the top 7 features — distance_km, hub_tier, hub_daily_capacity, n_stops, promised_hours, rain_flag, sale_event_flag. All five noise columns (label_print_batch, tape_roll_no, sticker_serial_mod, shelf_slot_no, scanner_build_no) have F-scores below 10 and rank 8 or lower. Their combined forest importance is 0.2244 (band 0.15–0.30): the forest still distributes some importance to them, but the signal features clearly dominate.

Feature count (part_c_selectk.csv): k = 7 gives the highest validation F1 (0.8333). k = 5 drops to 0.6988; k = 10–17 all fall between 0.78 and 0.80. The top-7 signal features are the sweet spot.

Tuning on the 7 selected features (part_c_tuning.csv):
| search | candidates | total fits | best CV accuracy | val_f1 |
|---|---|---|---|---|
| grid_search | 27 | 135 | 0.8952 | 0.7750 |
| randomized_search | 9 | 45 | 0.8905 | 0.7848 |
| default_forest_same_7_features | 1 | 1 | — | **0.8333** |

The untuned default forest (n_estimators=100, max_depth=None, min_samples_leaf=1) beats both tuned searches on the validation set. With only 180 validation rows, the CV winner overfits the folds; the simpler default generalises better. The tie-break rule (default → grid → randomised) correctly selects the default.

Threshold selection (part_c_thresholds.csv): using the chosen pipeline's validation probabilities, the highest threshold with recall ≥ 0.80 is 0.50. At this threshold, validation precision = 0.7955, recall = 0.8333, F1 = 0.8140.

Final test evaluation (part_c_final_test.csv): applying threshold 0.50 to the 180 test rows (41 delayed) gives precision = 0.6889, recall = 0.7561, F1 = 0.7209. Test recall (0.7561) is below the validation recall (0.8333) — expected because the threshold was calibrated on the validation set and the test set is small (41 positives means each parcel shifts recall by ~2.4 %).

Final configuration (part_c_final_config.csv): selector k = 7, n_estimators = 100, max_depth = unlimited, min_samples_leaf = 1, threshold = 0.50, chosen_from = default_forest_same_7_features.

Limitations

Synthetic data. Every row comes from generate_data.py, so relationships are cleaner than real logistics data. Real results would differ, and the accuracy figures here should not be expected to carry over.
Small evaluation sets. Validation and test each have 180 parcels, and the test set contains only 41 delayed parcels, so precision, recall and F1 on it are noisy. A change of a few parcels moves them noticeably.
Choices made on one split. The decision-tree depth, the model ranking and the alert threshold were chosen on a single 180-row validation split, so they can shift with a different split (the regression ranking already disagrees between validation and cross-validation).
Test set used once, for a different model than the one I would ship. The regression test score was computed for linear regression, not gradient boosting (see Model results).
Hub segments are based on 24 hubs and 50 parcels each. Segment membership could change with more data.
